## Non-negotiable epistemic UX invariants

```text
CURRENT != STALE
UNKNOWN != ZERO
REQUESTED != EXECUTED
EXECUTED != VERIFIED
VERIFIED != ASSURED
PROPOSED != AUTHORIZED
CAPABILITY != AUTHORITY
UI_DOES_NOT_CREATE_AUTHORITY
VISIBLE_EDGE != PROVEN_CAUSALITY
OBSERVATION_FAILURE -> NOT_PROVEN
```

These distinctions must survive compact cards, lists, graph views, timelines, notifications, and accessibility modes.

## Android-first validation tasks

Íris should explicitly test/design for:
- one-hand Home scan;
- narrow width and text scaling;
- bottom-sheet inspector;
- no hover dependencies;
- state label persistence in compact mode;
- long timelines;
- dense evidence lists;
- graph touch selection and pan/zoom without accidental state/action confusion;
- accessible chart summaries;
- offline/stale/unknown states;
- recovery and assurance distinction.

## State-first action discipline

Critical action placement must follow:

```text
STATE
→ CONTEXT
→ EVIDENCE
→ AUTHORITY CONDITION
→ AVAILABLE ACTIONS
```

Until downstream authorization exists, future operational controls should appear only as clearly marked future behavior/specification, not as apparently executable disabled buttons.

## Íris decisions required

### 1. Screen architecture
Confirm/refactor Home, Operations, OCS, Evolution, Conversation, and deep-domain navigation.

### 2. Design system
Freeze candidate semantic token architecture for:
- typography;
- spacing;
- radius;
- elevation;
- borders;
- states;
- freshness;
- evidence;
- authority;
- graph nodes/edges;
- charts;
- motion;
- density modes.

### 3. Component system
Define variants, anatomy, composition rules, invalid combinations, and compact/mobile behavior.

### 4. Golden paths
At minimum:
- Founder reads institution health;
- Founder traces a blocker to evidence;
- Founder inspects one OCS;
- Founder distinguishes stale vs unknown vs conflict;
- Founder traverses Atlas from OCS to evidence;
- Founder understands recovery vs assurance;
- Founder sees pending decision without implying automatic authority.

### 5. Accessibility
Produce explicit checks for contrast, text scaling, screen reader semantics, graph textual alternatives, touch targets, motion, and non-color state encoding.

### 6. Figma readiness
Once Lyra's brand decisions are available, identify which prepared frames can be materialized directly and which need structural revision first.

## Acceptance criteria

Ready for design truth materialization when:
- all critical epistemic states are distinguishable;
- mobile navigation preserves context;
- Home can be understood before drill-down;
- evidence is reachable from material claims;
- graph inspection remains reversible and non-semantic-producing;
- accessibility has explicit treatment;
- Lyra brand semantics are integrated without compromising state semantics;
- implementation affordances do not create false authority.
